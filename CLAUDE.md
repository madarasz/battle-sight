# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Battle Sight is an augmented reality overlay for Warhammer 40k: Kill Team. A fixed camera looks down on the board. The app finds the board with AprilTags, rectifies the image to board millimetres, and draws measurements (inch grid, rings, rim-to-rim distances, token ranges, door bands) on the video.

Read these before design work:

- `specs/about-project`: the owner's goals, in their own words.
- `specs/plan.md`: decisions, the 7 priorities with "done when" tests, risks, stack, and target layout. The plan is the source of truth for scope. Priorities 1 (board corners) and 2 (rectify) are done. Priority 3 (bases) is in code; its done test passes on the 2 test photos with an empty-board reference, not on the 2 without. Priority 4 (operative ID) is in code; its done test waits for a real gallery and a labelled game photo. Priority 5 (rings and distances) is in code; its done test waits for a tape measure check on the real board. Priority 6 (terrain layouts: map files, skill `record-map`, overlay) is done. Priority 7 (tokens) is next.

Work goes in priority order (1 corners, 2 undistort and rectify, 3 bases, 4 operative ID, 5 rings and distances, 6 terrain layouts, 7 tokens). Each priority has a measurable done test in the plan. Use it as the acceptance check.

## Documentation rules

- `README.md` is for non-technical users who install and run the app. It tells what the app does, how to start each mode, the keys, what the overlay shows, and fixes for common problems. Keep code internals, tests, config internals, module names, and development steps out of it. Write in ASD-STE100 Simplified Technical English.
- `README.md` starts with a "Work in Progress" list: one line per priority with a status emoji (✅ done, ⏳ in progress or next, 🚧 not started). Update it when a priority starts or passes its done test. Keep each line short.
- `README.md` "Setup" is only a short list that links to `docs/setup.md`. Put all setup and calibration steps (install, print tags, place cards, camera, `data/board.toml` values a user sets, lens calibration) in `docs/setup.md`, for the same non-technical reader.
- Technical and development information (architecture, algorithms, tolerances, tests, layout) goes in this file, `docs/cli.md`, or `docs/testing.md`.
- When a new priority adds a user-facing mode, key, or overlay, update the README "How to use" and "What you see" sections. When it adds a setup step, update `docs/setup.md`.

## Architecture

- `src/battlesight/` is the package (hatchling, `src` layout). Entry point `battlesight = battlesight.app:main`. `app.py` holds the argparse parser: no command = the live app (`cmd_live` builds a `live.LiveSession` and calls `ui.shell.run_window`; its options are on the main parser), plus the subcommands `enroll`, `gallery`, `calibrate`, `image-pipeline`. A new live feature is an entry in `live.ACTIONS` with a handler in `LiveSession`, not a new subcommand or option. `docs/cli.md` "All commands" lists every command.
- `live.py`: game core of the live app, no window, no camera, no GUI toolkit. `LiveSession.step(frame)` (None = camera down) returns a `LiveFrame` (image with board overlays only, JSON-safe `state`, `scale`). `LiveSession.dispatch(action_id, **args)` does one action of `ACTIONS`. `Action.enabled` and `checked` only tell a front end how to show a control; `dispatch` does not read them. `shell = True` actions (help, quit) belong to the front end. Status text and the name menu are drawn by the front end from `state`. All calls come from one thread. `specs/ui.md` is the UI plan: many layouts on this contract.
- `ui/` (PySide6, imported only inside `cmd_live`): `shell.py` has `Worker` (a `QThread` that owns the camera and the `LiveSession`; the GUI sends commands to its queue, they run between frames; old frames are dropped), `MainWindow` (one `QShortcut` per action, menu generated from `ACTIONS`, status bar, name popup, `set_layout`; `dispatch` drops commands while `state["busy"]`), `run_window`. `parts.py` has the shared widgets: `VideoWidget` (`NoFocus`, widget to image pixels), action controls, `MapPicker`, `DebugView`, `OperativeList`, `CandidateList`. `layouts/` holds `LAYOUTS` (`rosters` = default, top bar with View / Commands / Inspector / Reference / Debug sections and a `TeamRoster` each side; `inspector` = state-driven panel with the name list; `panel` = controls generated from `ACTIONS`, name popup). A layout only places widgets and uses `shell.dispatch`, `shell.new_video`, `shell.selected_crop`, `shell.show_debug`. It must not import `pipeline`, `ident`, `calib` or `camera` (a test checks this). Every control and list needs `NoFocus`, or `space` pushes it. `settings.py` (no Qt) reads and writes `data/ui.toml` (git-ignored, no command option; a bad file gives a notice, never a stop). Never call `cv2.imshow` or `cv2.waitKey` in the live app. Tests run offscreen: `tests/test_ui.py`.
- `pipeline.py`: single-frame analysis, no camera or window. Stages are `corners`, `rectify`, `bases`, `ident`. Stages register in run order with `@stage(name, draw=..., views=...)` (`views` returns extra named images, `--out` writes them as `<name>.<view>.jpg`) and return a `StageResult` (ok, message, JSON-safe `data`). A failed stage skips the later ones. `Pipeline.analyze(frame, until=...)` stops early (the live `b` key). `Pipeline.analyze` gives a `FrameResult` (`to_dict()` is the JSON report, with `schema` version), `Pipeline.annotate` draws all stage overlays. Add each new priority as a stage here, so the live app, the `image-pipeline` subcommand and tests pick it up. The `image-pipeline` subcommand exit codes: 0 all stages ok, 1 a stage failed, 2 bad input.
- `circles.py` (priority 3): `find_circles` finds round bases of the known diameters (`[bases]` in `data/board.toml`, base bottom) in a top-down image at `bases.px_per_mm` (4). Edge votes along the gradient for proposals, 120 rays with a dark-rim test, robust free fit, nearest size class, fixed-radius refit, `coverage` = visible rim part. `foreground_mask` diffs against an empty-board reference. `Pipeline(reference=frame)` / `set_reference` warps the reference from its own tags into `cache["bases_reference"]`; the `bases` stage then runs in `reference` mode, else `single_frame` (finds some dark-ringed tokens and barricades). The stage puts `bases` (list of `Circle`) in `scratch`. Known sizes (roster): `Pipeline(roster=...)` / `set_roster`, else `Gallery.base_sizes()` (`team.toml`), else all `diameters_mm`; `LiveSession` sets it from `ident.roster_sizes` at the start. With known sizes `detect_bases` searches only these and keeps the radius in the fit (`_verify_fixed`; a free fit goes to the model when part of the rim is hidden), and with a reference too the limit is `reference_min_coverage` (0.4). Without known sizes the fit is free: do not use the fixed radius with all config sizes, and do not lower the coverage without a reference (both measured worse, `specs/bases-benchmark.md` 11.1). `pipeline.BasesSearch` limits one search (the enroll zoom area, known size, `relaxed` = second search with `[bases] relaxed_*`, results need a click). Bottom edge lies on the play surface: no parallax correction. `docs/cli.md` "Base detection" has the steps and config keys.
- `ident.py` (priority 4): crop around each base from the bases image (`store_crop` keeps 40 mm board each side, `prepare` cuts `ident.crop_pad_mm`, turns, masks a circle, resizes to `input_px`), `Embedder` (`DinoEmbedder` = DINOv2 via `transformers`, MPS, lazy load; `ColorEmbedder` = `model = "color-hist"`, no ML, used by all unit tests), `Gallery` (`data/teams/<team>/team.toml` with `base_mm`, `<operative>/*.png`, `<operative>/bg/` empty-board crop of each photo (optional), `mask_crop` (`ident.mask` switch in `data/board.toml`: grey on all but the operative, raw and masked embeddings side by side, `can_mask`, per-base fallback to the full crop), `embeddings.npz` cache, `rotations` angles per crop, score = mean of `top_k` best photos, `leave_one_out`), `assign` (size-class limit, Hungarian one-to-one, `min_score` unknown, `min_margin` unsure), `Gallery.add` raises `DuplicatePhoto` for a crop with the same pixels as a photo of that operative (`same_photo`), `Gallery.hidden` = file indexes that `scores` skips, `LabelSession` (click fix logic, no window calls; `choose` returns None and `undo` (done, path) for a fix that added no file), `IdentTruth` / `score_truth` (done test). Labels are `<team>/<operative>`. Stage `ident` after `bases`: always ok, names nothing without a gallery (`Pipeline(gallery=...)`, `image --team`). The bases stage puts `bases_image` in `scratch`, the ident stage `base_crops` and `idents`. `docs/cli.md` "Operative identity" has the steps and config keys.
- `bench.py`: bases benchmark, pure functions. Ground truth `<name>.bases.json` schema 2 (`Truth`, `Decoy` = `not_bases`, `roster_mm` = base sizes of the teams, given to the stage by the tool and the photo tests; schema 1 still loads), `match` (one-to-one global greedy within `tol_mm`, false detections get a `kind`, `inside_base` or `other`), `PhotoScore` (`done_ok` = priority 3 done test), `metrics` / `total` (recall, precision, f1, size accuracy, centre error of clear clicked or detector rims), `report` (`bench.json`), `compare` (baseline rules), text table. Also the photo file rules (`find_photos`, `reference_path`: `<name>.empty.*` is a reference). `pipeline.detect_bases(img, cfg, reference)` is the body of the bases stage, so `tools/bench_bases.py` runs corners and rectify once and sweeps `[bases]` values cheaply. `tools/annotate_bases.py` holds the click logic in `Annotator` (no window calls, unit tested).
- `ident_bench.py`: identification benchmark on `<name>.ident.json` photos. `score` splits losses by cause (`right`, `wrong`, `unknown` = naming; `wrong_size`, `missed` = detection, operative size from the gallery), `metrics` (`accuracy` = done test, `naming_accuracy` = only correctly detected bases), `report`, `compare` (baseline rules, per-photo `right` too), `gallery_state` (content hash of the git-ignored gallery; `same_gallery` guards each compare), `copies_of` (gallery photos that show the same frame as a found base of the test photo, from a name fix on `--image-source`; `run` hides them for that photo, metric `hidden`), `run` (shared by `tools/bench_ident.py` and `test_ident_benchmark_no_worse`). The baseline `tests/images/ident_baseline.json` moves only on purpose, never only to make a test pass.
- `tests/test_photos.py` (marker `photos`, off by default through `addopts` in `pyproject.toml`): runs the pipeline on each photo in `tests/images` and compares with the reviewed `<name>.expected.json` next to it (the `--out` report), corners within `CORNER_TOL_MM` (1 mm, converted with the tag's pixel size). Never update an expected file only to make a test pass. Bases: `<name>.bases.json` is ground truth (`clear` / `hidden` rims, `tol_mm`, `source`, `not_bases`), `<name>.empty.jpg` an optional empty-board reference. Bases and names have no all-found test: not all bases can be found. `test_bases_benchmark_no_worse` and `test_ident_benchmark_no_worse` fail only when the result is worse than `tests/images/bases_baseline.json` or `ident_baseline.json` (totals and per photo); `pytest -m photos` prints the metrics tables with the `done` column of each done test. The baseline moves only on purpose (`tools/bench_bases.py --write-baseline`, new numbers in the commit message), never only to make a test pass.
- `config.py`: `BoardConfig` (frozen dataclass) loads `data/board.toml`. All lengths are in mm. Board coordinates: origin at the top-left board corner, x right, y down. Corner index 0..3 = TL, TR, BR, BL, and `tags.ids[k]` is the tag at corner k.
- `calib.py`: `TagDetector` (OpenCV `cv2.aruco` with `DICT_APRILTAG_36h11`, no contrib build) returns `{tag_id: TagObs}`. Each card lies under a board corner, tag outside the board, diagonal to the corner. `board_corners_px` takes tag corner k+2 (the one nearest the board) and pushes it toward the board by the white card margin to get board corner k. `DriftMonitor` auto-locks a reference after `settle_frames` still frames, then reports OK / MOVED / CARD_MOVED / LOST. After a move it waits for `settle_frames` still frames again: when all four cards moved as one piece (`card_offset_mm`, leave-one-tag-out homography, within `drift.tolerance_mm`) it saves the new position (`relocked`), else CARD_MOVED names the card. No manual re-lock key. It converts pixel shift to mm with each tag's apparent size.
- `calib.py` also holds `Lens` (K, distortion, `undistort_px` / `distort_px`), `lens_for_frame(camera, size)` (the `[lens]` calibration of `CameraSettings` when its aspect ratio fits the frame, else a nominal pinhole from `CameraSettings.focal_35mm`), and the ChArUco target and `calibrate_lens`.
- `rectify.py`: `fit_view` fits a `BoardView` (homography board-surface mm -> undistorted px) to the 16 tag corners, with the board thickness correction from the planar camera pose. `warp_board` makes the top-down image. `measure_edges` and `measure_grid_lines` check it (board edges, printed grid lines). The rectify stage puts `view` and `rectified` in `scratch` for later stages.
- Map grid: `[grid]` in `data/board.toml` and `BoardConfig.grid_lines_mm()`. Tomb World uses its 7 x 6 printed sections inside a 12 mm margin, Volkus a 1 in pitch. Never hard-code an inch grid. `docs/cli.md` "Map grid" documents it.
- `camera.py`: `Camera` wraps `cv2.VideoCapture` and reconnects after repeated read failures. `read()` returns `None` while the camera is down. Callers must handle that. `ImageSource` has the same calls for one image file (`--image-source`). A device index uses AVFoundation on macOS (Camo, built-in camera). A URL (`is_stream`) uses FFmpeg with open and read timeouts, and `LatestFrameReader` reads it on a thread and keeps only the newest frame. `CameraSettings` loads and saves `data/camera.toml` (git-ignored, machine-local): `[camera]` from `tools/list_cameras.py`, `[lens]` from `calibrate`. Each writer keeps the other table. `app.py` `_apply_camera_settings` fills the camera options left out on the command line from it: option > file > built-in default. `docs/setup.md` has the camera troubleshooting (Camo extension blocked by MDM, stream network checks).
- `measure.py` (priority 5): pure geometry in board mm, no window. `ring_radius_mm`, `rim_gap` (distance and end points on the rims, 0 for touching bases), `base_at` (hit test, `LabelSession.base_at` uses it). `LiveSession` holds `selected`, `target`, `ring_in`, also without names (after `b`); `LabelSession.selected` is not used by the live app. `LiveSession.frozen` = the snapshot is on the screen; `Esc` (`snapshot.back`, "Go back to Live") only clears it, so bases, names and selection stay on the live video (mapped with the live `BoardView`) until the next snapshot. A click without a base under it selects a hatchway or breach point (`selected_opening`). `team.set(slot, name)` changes the teams at run time (gallery loads again at the next `space`); `base.select(index)` selects from a team list. Left click (`board.click`): select, then set or move the target. Right click (`board.select`): replace the selection, the shell then opens the name popup in layouts with `name_popup`. A new selection clears the ring and the target.
- `terrain.py` (priority 6): terrain map files `data/maps/<terrain>/<layout>.toml` (committed), written by an agent from a layout card photo with the project skill `.claude/skills/record-map/` (reading rules there), not detected. `load_map` / `parse_map` check the file (`MapError`) and turn grid points `[col, row]` (0.5 steps) or `at_mm` into board mm. Each wall has its card `key` (A = 2 grid, B = 1 grid; A walls except `[terrain] no_middle_pillar` have a middle pillar) and `opening = true|false` (breach on `[terrain] breach_walls`, else hatchway); an opening sits at the centre between two pillars (`opening_at` picks the half of an A wall with a middle pillar). `shapes` gives footprints with the `[terrain]` sizes of `data/board.toml`; `overlay.draw_terrain` draws them. `list_maps` feeds the live actions `map.terrain_type`, `map.layout`, `view.terrain` ("Layout"), `view.zones` ("Drop zones", off at start), `view.keys` ("Terrain keys", off at start: wall keys and `T` on pads, drawn last) (no keys, no options: `ui/parts.MapPicker` drop-down lists at the top of each layout panel, choice saved in `[map]` of `data/ui.toml`). Command `map` checks and draws files. `docs/cli.md` "Terrain maps".
- `overlay.py`: draw-in-place helpers on BGR frames. Line and font sizes scale from a 1080p baseline, so overlays stay readable at 4K.
- `tests/conftest.py`: `render_board` makes a synthetic top-down board with the board resting on real square AprilTag cards, tags outside the corners, with an optional homography, pixel shift, printed grid lines, and `bases` (`Base`: black rim, lighter top, model over part of the rim), `walls`, `discs` (tokens, prints). `tomb_world_grid()` is a test config with the Tomb World size and sections. `tests/test_rectify.py` adds a virtual pinhole camera for exact thickness and distortion tests. It returns the image and an `mm2px` function for ground truth. New vision tests should use this harness, not camera captures. `make_config(**over)` builds a test config without the TOML file.

- Corner cards (`tools/make_tags.py`): 90 mm square, tag in the outer quadrant, black L in the inner quadrant at the board corner. The 5 mm white margin is the tag quiet zone. The app measures from the cards, not the board: a board that slides over a still card gives no warning.
- Rectify: the top-down image scale is `rectify.px_per_mm` (default 2 px per mm). `board.width_mm` is the edge from tag 0 to tag 1 as the cards lie (703 x 606 mm in the test photos). When width and height are swapped, the stage fails and says so. Board thickness: the cards lie on the table and the play surface is `board.thickness_mm` higher (Tomb World 1.0 mm, caliper). Without the correction, 1 mm gives up to about 0.5 mm error at the board edge, 3 mm about 1.5 mm. With `grid.printed = true` the stage finds the printed lines and reports their offsets, a check that does not use the tags.
- Lens: without a `[lens]` table in `data/camera.toml` the app uses a nominal lens (`focal_35mm`, default 24 mm, no distortion). Phones correct most distortion themselves. All camera values live in `data/camera.toml`, none in `data/board.toml` (a `[camera]` table there is an error). `Pipeline(cfg, until, camera)` takes the `CameraSettings`; tests and photo tests use the default (nominal lens), and `tests/conftest.py` points the CLI at a temporary camera file.

## Design constraints from the plan

- All measurement is 2D in the board plane. No vantages or heights in the MVP. Measure to the base rim, never to the model body (parallax moves the model about 19 mm at a board corner).
- Base detection (geometry: background subtraction plus known-radius circle fit) stays separate from operative identity (DINOv2 embedding plus few-shot gallery). A new team must only need gallery photos, never a retrained detector.
- Walls are not tracked. Doors are clicked once per map, snapped to the grid, and saved as a named map file.
- The core must not depend on Qt. A later FastAPI and browser front end must reuse it. An OpenCV `imshow` window is enough for priorities 1 and 2. PySide6 comes later.
- Board size, tag sizes, tolerances, base, token, and door sizes are config values, not constants. A second board (Volkus, 559 x 760 mm) is planned.

## CLI design principles

- Use as few command-line options as possible. When a key (later a UI button) can turn a feature on or off, or change a mode or view, do not add an option for it. Options are only for values that the user cannot change while the app runs (camera source, config file, teams).
